# Phase 1 — ERP + Factory application source-size policy

Phase 1 status: policy implemented on audit/loc-300-500-20261113, not merged into main.

## Rules
- More than **300 physical lines** (301–500) in application source: CI warning only.
- More than **500 physical lines**: CI failure for a new file, a previously compliant file, or an oversized legacy file that grows.
- Legacy files already over 500 at the frozen source snapshot `b5d5fea32ab435861ea77a38905eefdd42e64846` may remain while phased refactoring continues, but may not exceed that original size.
- Pull requests also compare every still-oversized file to the merge-base of the PR and the destination branch. If it has shrunk on main, it must not grow back during a later change. Renames or reintroduced oversized paths are treated as new files.
- Line counts include whitespace and comments (physical source lines), not complexity estimates. Exactly 300 passes without warning; exactly 500 passes with a warning.

## Coverage
Eligible extensions: `.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.mts`, `.cjs`, `.css`, `.scss`.
Application roots: `client/src/`, `server/`, `shared/`, `desktop/`, `build/`.
Non-application files such as tests, translations, scripts/tooling, schema/migrations, generated outputs and other repository material are measured or otherwise classified but not hard-blocked under this Phase 1 policy. They retain their separate existing safety contracts.
Generated exceptions apply only to files with `.generated.` or inside `generated/` or `__generated__/` directories. Deliberately broad exceptions for live ERP application pages are not permitted.
Architecture constraints in `config/god-file-boundaries.json` still apply independently, including stricter limits for selected composition roots.

## Frozen audit baseline
The original audit was obtained from main on 13 November 2026 (historical reference). The enforcement baseline is instead the 14 November 2026 main commit immediately preceding this phase, to avoid retroactively failing unrelated changes already on main:
- 6,537 counted source files, including 4,222 application files.
- 530 application files over 500 lines (initial split backlog).
- 660 application files at 301–500 lines (warning backlog).
- 3,032 application files at or below 300 lines.
- Other oversized files are tracked separately: 90 tests, 36 translations, 12 tooling, and 4 schema/migration files.

On the enforcement baseline, 4,223 application files were counted: 531 above 500 lines, 660 at 301–500 lines and 3,032 at or below 300. These figures supersede the historical 530-file split backlog for Phase 1 enforcement. The older 13 November counts remain audit history, not the current guardrail ceiling. The JSON report generated by each CI run is the authoritative measurement for that commit.

## Verification and workflow
- Run `node --test tests/file-line-policy.node.test.mjs` to test boundaries, classifications and ratchet behavior.
- Run `node scripts/audit-file-lines.mjs --output artifacts/code-line-policy/report.json` for local baseline validation (requires git history).
- On pull requests, the Code file line limits workflow also passes `--compare-ref` against the PR destination SHA to block re-growth after a reduction.
- The workflow uploads the complete per-file JSON report and writes a GitHub job summary.
- The implementation uses Node built-ins and Git only. It does not change accounting, database migrations, supplier balances, inventories, API handlers, endpoints or frontend behavior.
- Avoid implementing multi-file splits until Phase 2 dead-code cleanup and targeted regression tests are complete.
